# План исправления отображения Tool Events в UI

## Анализ проблемы
- Tool block создается при событии `ai_chunk` с `kind: 'tool'`, но не обновляется при последующих событиях `message.part.updated` для tool parts.
- Пользователь видит только начальный статус "pending" и "No input", без обновлений input/output в реальном времени.
- Отсутствует обработка событий `message.part.updated` с `part.type === 'tool'`.
- Бэкэнд (backends/kilo-agent-backend.mjs) уже отправляет события `message.part.updated` для tool parts, но фронтенд их игнорирует.

## Структура данных событий
Из лога видно последовательность:
1. `message.part.updated` с `state.status: 'pending'` - создание блока
2. `message.part.updated` с `state.status: 'running'` и `input` - обновление статуса и input
3. `message.part.updated` с `state.status: 'completed'` и `output` - финализация с output

## Необходимые изменения

### 1. Обновление JavaScript (public/index.html)

**Место внедрения:** Функция `handleWsMsg`, после обработки существующих событий

**Код для добавления:**
- В switch/if блоке обработки событий добавить case для `stream_event`
- Распарсить событие: `const eventData = JSON.parse(d.data.event);`
- Проверка: `if (eventData.type === 'message.part.updated' && eventData.properties?.part?.type === 'tool')`
- Селектор для поиска блока: `document.querySelector(\`[data-part-id="\${partId}"]\`)`
- Обновление DOM элементов: `.tool-input code`, `.tool-output code`

**Точка внедрения в handleWsMsg:**
- После обработки `ai_chunk` событий
- Перед или после обработки `message.part.delta`
- Примерная строка: ~350-400 (в зависимости от текущей структуры)

**Обработка граничных случаев:**
- Если tool block еще не создан при получении `running` - создать его
- Если `input` или `output` = null/undefined - не обновлять соответствующий блок
- Если несколько tool вызовов одновременно - каждый со своим `data-part-id`
