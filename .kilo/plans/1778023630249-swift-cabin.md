# План исправления статусов tool-ивентов в KiloAgentBackend

## Цель
Обеспечить корректную генерацию и передачу событий инструментов (tool events) со всеми статусами (pending, running, completed, failed) от Kilo-стрима до фронтенда через server.js.

## Текущий анализ
- **KiloAgentBackend** (`backends/kilo-agent-backend.mjs`) обрабатывает события SSE: `message.part.updated`, `toolpartupdated`, etc.
- В `message.part.updated` для tool частей вызывается только `onToolProposal` один раз при инициализации.
- Статусы инструментов (`pending`, `running`, `completed`, `failed`) обрабатываются в событии `toolpartupdated`, где вызываются соответствующие колбеки.
- **server.js** вешает колбеки `onToolProposal`/`onToolStart`/`onToolComplete`/`onToolError` и отправляет WebSocket сообщения с `status: 'pending'|'running'|'completed'|'failed'`.
- Проблема: статусы приходят в `message.part.updated` (part.state.status), но логика вызывает колбеки только в `toolpartupdated`. Нужно добавить обработку статусов в `message.part.updated` для native режима.

## Шаги реализации

### 1. Изменения в KiloAgentBackend (backends/kilo-agent-backend.mjs)
1.1. В блоке обработки `event.type === 'message.part.updated'` добавить логику для tool-частей:
   - После сохранения partData добавить проверку `if (partType === 'tool')`
   - Получить `status = part.state?.status`
   - Добавить логи: `console.log('[KiloBackend TOOL STATE]', { partID, toolName: partData.tool, status });`
   - Добавить логи для part: `console.log('[KiloBackend] TOOL part.updated', JSON.stringify(part).slice(0, 200));`

1.2. Добавить флаги в partData:
   - `started: false` - для предотвращения двойных вызовов onToolStart
   - `finished: false` - для предотвращения двойных вызовов onToolComplete/onToolError

1.3. Для native режима (`!isBuffered`) вызывать колбеки в зависимости от статуса:
   - `if (status === 'pending' && !partData.proposed)`: вызвать `callbacks.onToolProposal({ tool: partData.tool || 'unknown', input: '', partID })`, установить `partData.proposed = true`
   - `if (status === 'running' && !partData.started)`: вызвать `callbacks.onToolStart({ tool: partData.tool || 'unknown', input: '', partID })`, установить `partData.started = true`
   - `if (status === 'completed' && !partData.finished)`: вызвать `callbacks.onToolComplete({ tool: partData.tool || 'unknown', input: '', output: '', partID })`, установить `partData.finished = true`
   - `if (status === 'failed' && !partData.finished)`: вызвать `callbacks.onToolError({ tool: partData.tool || 'unknown', input: '', error: part.state?.error || 'Unknown error', partID })`, установить `partData.finished = true`

1.4. Сохранить существующую логику для `part?.time?.end` (вызов onToolComplete по завершению части), но учесть флаги `finished`.

### 2. Изменения в toolpartupdated (предотвращение дубликатов)
2.1. В блоке `else if (event.type === 'toolpartupdated')` добавить проверку перед вызовом колбеков:
   - Получить `partData = messageParts.get(partID)`
   - Если `partData.started` для running, `partData.finished` для completed/failed - пропустить вызов колбека
   - Добавить комментарий: "Статусы могут приходить как через toolpartupdated, так и через message.part.updated"

### 3. Логирование для отладки
- Добавить временные логи перед каждым tool-колбеком: `console.log('[KiloBackend TOOL STATE]', { partID, toolName, status });`
- Добавить логи в начале блока tool в message.part.updated: `console.log('[KiloBackend] TOOL part.updated', JSON.stringify(part).slice(0, 200));`

### 4. Сохранение интерфейса
- Не менять сигнатуры колбеков в `createCallbackWrapper`
- Сохранить формат объектов, передаваемых в server.js (tool, input, output?, error?, partID)
- server.js уже корректно обрабатывает все статусы

## Критерии приемки
- При запросе, триггерирующем инструмент (glob/bash):
  - Логи server.js: `[WS SENDING TOOL] glob pending`, затем `running`, затем `completed`/`failed`
  - Логи KiloBackend: соответствующие `[KiloBackend TOOL STATE]` записи
  - WebSocket стриме: ai_chunk с payload.kind = 'tool' и status в последовательности pending → running → completed/failed
- Поведение onText и onReasoning не изменяется
- Нет двойных вызовов колбеков
