# План исправления отображения tool events в UI

## Описание проблемы
Tool events от Kilo агента (toolpartupdated, message.part.updated с type: 'tool') присутствуют в логах, но не отображаются в UI чата. Отсутствует обработка переходов состояний tool (pending → running → completed).

## Текущая архитектура
- `backends/kilo-agent-backend.mjs`: Обрабатывает события от Kilo сервера, но игнорирует 'toolpartupdated' и не отслеживает состояния tool parts.
- `server.js`: Получает callbacks от бэкенда, но tool callbacks пустые и не отправляют события в WebSocket.
- `public/index.html`: Обрабатывает tool chunks, но не поддерживает состояния и обновления.

## План реализации

### 1. Исправление backends/kilo-agent-backend.mjs
**Цель:** Добавить обработку события 'toolpartupdated' и отслеживание состояний tool parts.

**Изменения:**
- Добавить Map `toolPartsMap` для хранения tool parts по partID
- В обработке `message.part.updated` сохранять tool parts с type === 'tool'
- В обработке `toolpartupdated`:
  - Использовать структуру `const { partID, tool: toolName } = event.data;`
  - Получать tool part из Map
  - Определять статус из `toolPart.state?.status || toolPart.status`
  - Извлекать input как `input?.command || JSON.stringify(input, null, 2)`
  - Для failed статуса брать error из `toolPart.error || toolPart.state?.error || 'Unknown error'`
  - Вызывать соответствующие callbacks: `onToolProposal`, `onToolStart`, `onToolComplete`, `onToolError`
  - Обработка race condition: если tool part не найден в Map, буферизовать событие
    ```javascript
    // Если tool part не найден в Map:
    if (!toolPart) {
      // Буферизовать событие на 100ms и повторить поиск
      pendingToolEvents.push({ partID, toolName, retry: 0 });
      setTimeout(() => retryToolEvent(partID), 100);
      continue;
    }
    ```
  - Учитывать buffered mode: буферизовать tool events и отправлять после reasoning
    ```javascript
    // В kilo-agent-backend.mjs для buffered mode:
    if (mode === 'buffered') {
      bufferedToolEvents.push({
        partID, toolName, status, input, output,
        timestamp: Date.now()
      });

      // Отправить все tool events после завершения reasoning
      if (reasoningFinished) {
        bufferedToolEvents
          .sort((a, b) => a.timestamp - b.timestamp)
          .forEach(toolEvent => {
            callbacks.onToolComplete?.(/*...*/);
          });
      }
    }
    ```
- Добавить логирование tool events в консоль

**Файлы для изменения:**
- `backends/kilo-agent-backend.mjs` (строки ~202-646, функция `processSend`)

### 2. Исправление server.js
**Цель:** Обновить callbacks для отправки tool событий в WebSocket как ai_chunk с kind: 'tool'.

**Изменения:**
- В функции `runCliSingle` обновить callbacks:
  - `onToolProposal`: Отправлять {type: 'ai_chunk', kind: 'tool', status: 'pending', input: inputText, partID}
  - `onToolStart`: Отправлять {type: 'ai_chunk', kind: 'tool', status: 'running', input: inputText, partID}
  - `onToolComplete`: Отправлять {type: 'ai_chunk', kind: 'tool', status: 'completed', input: inputText, output: outputText, partID}
  - `onToolError`: Отправлять {type: 'ai_chunk', kind: 'tool', status: 'failed', input: inputText, error: errorText, partID}
- В каждом событии передавать status, input (как string), output (если есть), error (если есть), partID
- Добавить логирование отправки tool событий: `console.log('[WS SENDING TOOL]', toolName, status);`

**Файлы для изменения:**
- `server.js` (строки ~2434-2442, callbacks в `runCliSingle`)

### 5. Отладка и тестирование
**Цель:** Добавить логирование для проверки корректности работы.

**Изменения:**
- В `kilo-agent-backend.mjs`: логировать `[TOOL EVENT]` для каждого состояния
- В `server.js`: логировать `[WS SENDING TOOL]` при отправке
- В `index.html`: логировать `[UI RECEIVED TOOL]` при получении

### 6. Обработка edge cases
**Цель:** Обеспечить корректную работу в нестандартных ситуациях.

**Изменения:**
- Пустой output (tool завершился без вывода) - показывать "No output"
- Tool timeout (долгое выполнение >30 сек) - добавить индикацию loading
- Tool approval (если требуется подтверждение пользователя) - обработка pending состояния
- Race condition: toolpartupdated до message.part.updated - буферизовать события
- Concurrent tools - корректное отображение нескольких tool blocks
- Binary output - проверка и обработка как string

**Критерии приёмки:**
- ✅ При выполнении команды (например, `ls -la`) появляется tool block с иконкой 🔧, названием "bash", статусом running → completed, input/output collapsed
- ✅ Tool block обновляется без дубликатов при нескольких updates одного tool
- ✅ Клик разворачивает input/output
- ✅ Несколько tool blocks одновременно (concurrent execution)
- ✅ Tool с ошибкой показывает status failed и error message
- ✅ Long output (>5000 chars) отображается с scroll
- ✅ Tool blocks сохраняются при переключении вкладок
- ✅ Tool block появляется в правильном порядке между reasoning и text (не в конце)
- ✅ При перезагрузке страницы tool blocks восстанавливаются из session history
- ✅ Copy button корректно копирует output в clipboard
- ✅ Логи видны в консолях сервера и браузера

## Риски и зависимости
- Требуется тестирование с реальным Kilo сервером для проверки событий
- Возможно потребуется настройка event-stream подписки в бэкенде
- UI изменения могут конфликтовать с существующими стилями
- Tool events могут приходить до message.part.updated (race condition)
- Нужна обработка concurrent tools (несколько bash команд параллельно)
- Output может быть binary (нужна проверка typeof output === 'string')
