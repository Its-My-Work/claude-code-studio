## Critical Context
- Из кода: // Check session lock to prevent simultaneous processChat for the same session
- Назначение: предотвращает одновременную обработку processChat для одной сессии, избегает race conditions и дубликатов.
- Работает через очередь: если locked, сообщение ставится в очередь sessQ.
- На вопрос о разных вкладках: да, два сообщения в разных вкладках могут обрабатываться одновременно, поскольку sessionLocks блокирует только по sessionId. Разные вкладки имеют разные tempId/sessionId, поэтому не конфликтуют.
- InitialSessionId: msg.sessionId || (tabId ? null : legacySessionId). Основание для locked: sessionLocks.has(initialSessionId) — если true, значит уже обрабатывается, ставим в очередь. Для set: если false, set(initialSessionId, true) — начинаем обработку, блокируя для других.
- Проблема с новой вкладкой: когда создается новая вкладка, msg.sessionId = null (currentSessionId = null), tabId = tempId. initialSessionId = null. Если sessionLocks.has(null) false (первое сообщение), set(null, true). После обработки, finally delete(localSessionId), где localSessionId - real sessionId от kilo, не null. Так что delete(null) не происходит, null остается locked, блокируя следующие сообщения в любых новых вкладках, пока сервер не перезапустится.
- Решение: изменить initialSessionId = msg.sessionId || tabId || legacySessionId; После вычисления localSessionId, добавить if (initialSessionId !== localSessionId) { sessionLocks.delete(initialSessionId); sessionLocks.set(localSessionId, true); } Это позволит использовать tabId как initial lock для новых вкладок, а затем перенести на real sessionId.
- Для legacy режима (без вкладок): initialSessionId = msg.sessionId || legacySessionId; работает как сейчас. Если tabId нет, решение не меняет поведение.
